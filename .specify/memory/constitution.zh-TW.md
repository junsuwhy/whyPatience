# whyPatience 專案憲章

## 核心原則

### I. 程式碼品質卓越

所有程式碼必須遵循嚴格的品質標準，包括一致的格式化、清晰的命名慣例、適當的文件記錄，以及可維護的架構模式。所有變更必須進行程式碼審查。靜態分析工具必須配置完成並在合併前通過檢查。技術債務必須被追蹤並系統性地處理。

理由: 高品質程式碼降低維護成本、提升開發者生產力，並確保專案的長期可持續性。

### II. 測試驅動開發 (不可妥協)

測試必須在實作前撰寫。所有功能需要全面的測試覆蓋，包括單元測試、整合測試和端對端測試。必須嚴格遵循紅-綠-重構循環。沒有通過測試並維持最低覆蓋率門檻的程式碼不得合併。

理由: TDD 確保軟體的穩健性和可靠性，並提供變更的信心。它作為活文件並防止回歸。

### III. 使用者體驗一致性

所有使用者介面必須遵循既定的設計系統和互動模式。使用者流程必須在所有接觸點保持直觀和一致。必須符合無障礙標準 (WCAG 2.1 AA)。必須定期收集使用者回饋並納入設計決策。

理由: 一致的使用者體驗減少使用者認知負擔、提升採用率，並確保產品對所有使用者都可用，不論其能力如何。

### IV. 效能標準

所有功能必須符合定義的效能基準，包括回應時間、吞吐量和資源使用。效能測試必須自動化並整合到 CI/CD 管道中。效能回歸被視為關鍵錯誤，必須立即處理。

理由: 效能直接影響使用者滿意度和業務成果。主動的效能管理避免日後昂貴的最佳化工作。

## 開發標準

程式碼必須遵循既定的模式和慣例撰寫。相依性管理必須明確且最小化。必須遵循安全最佳實務，包括輸入驗證、安全認證和資料保護。

所有變更必須經過同儕審查。文檔必須與程式碼變更同步更新。破壞性變更需要 RFC 流程和遷移文檔。

## 品質門檻

所有 Pull Request 必須通過自動化檢查，包括程式碼檢查、型別檢查、安全掃描和測試套件。程式碼覆蓋率必須維持最低門檻。效能基準必須達到或明確說明理由。

使用者介面變更必須進行手動測試。面向使用者的功能必須進行可及性測試。影響可擴展性的後端變更必須進行負載測試。

## 治理

憲章修正需要核心團隊成員的多數同意，並必須遵循語意化版本控制。所有原則都具有約束力，違反需要明確的理由和補救計劃。

每月進行合規性審查。原則違反被系統性地追蹤和處理。憲章優先於所有其他開發實務和指導原則。
